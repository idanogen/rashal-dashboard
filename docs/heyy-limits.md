# מגבלות heyy, וההגירה מגרסה 2

נמדד חי מול החשבון של עוגן ב-25-26/08/2026, ולא נלקח מהתיעוד בלבד.
המספרים כאן הם מה שהשרת החזיר בפועל, ולכן אפשר להסתמך עליהם.

---

## 1. מכסת הקצב: 100 בקשות לדקה

כל תשובה של heyy נושאת שלוש כותרות:

```
x-ratelimit-limit: 100
x-ratelimit-remaining: 99
x-ratelimit-reset: 1787683497      ⟵ חותמת יוניקס, בשניות
```

חלון **קבוע של דקה**, ו-`reset` אינו זז בתוך החלון (נמדד: חמש קריאות
רצופות החזירו את אותו `reset` בדיוק).

| תוכנית | בקשות לדקה |
|---|---|
| **Hobby (זו שלנו)** | **100** |
| Pro | 500 |
| Ultra | 1,000 |
| Enterprise | לפי הסכם |

🔴 **גם בקשה שנכשלת נספרת.** חמש קריאות שהחזירו 400 הורידו את המונה
מ-99 ל-94. לולאת ניסיונות חוזרים על שגיאת ולידציה שורפת את המכסה של
כל המערכת, ולכן **4xx לעולם לא נשלח שוב** חוץ מ-429.

🔴 **המונה משותף לכל הנתיבים ולכל הגרסאות.** הנתיב הישן
`api.heyy.io/api/v2.0/...` יושב באותו דלי בדיוק כמו `v3`.

חריגה מחזירה **429**:

```json
{"success": false,
 "error": {"messageKey": "rate_limit_exceeded",
           "message": "Too many requests. Limit is applied per minute per tenant."}}
```

### מה המערכת עושה עם זה

`api/_lib/heyy-rate-limit.ts` מחזיק את המדיניות, והיא נבדקת ביחידה.

- **429 עם איפוס קרוב** (עד 15 שניות): ממתינים ושולחים. הלקוח לא מרגיש.
- **429 עם איפוס רחוק**: מוותרים, מסמנים `retryable`, **והפריט חוזר
  לתור**. פונקציית Vercel חיה 60 שניות וחלון המכסה הוא דקה, ולכן אי
  אפשר להמתין לזה בתוך הבקשה.
- 🔴🔴 **5xx במסלול שליחה אינו נשלח שוב לעולם.** 429 אומר במפורש שהבקשה
  לא בוצעה, ולכן הוא בטוח. שגיאת שרת על שליחה היא דו משמעית, וייתכן
  שהוואטסאפ כבר יצא ללקוח. כפילות גרועה מהודעה חסרה.
- מסלול קריאה בלבד (תבניות, ערוצים) כן מנסה שוב על 5xx.

**עד 26/08/2026 לא היה כאן שום טיפול**, ו-429 נשמר כ-`status: 'failed'`
כאילו התוכן נדחה. מנוע הסקרים היה מסמן את השורה כנכשלה ומשחרר אותה רק
לבדיקה ידנית, כלומר **סקר שנחסם על מכסה היה נעלם לתמיד**, דווקא בשעה
העמוסה שבה יש הרבה מה לשלוח.

## 2. וובהוק

נקודת הקצה `POST /v3/api_webhooks/search` מחזירה כתובת, סטטוס ואילו
אירועים רשומים לאיזה ערוץ, ולכן אפשר לנטר את זה בלי להיכנס לממשק.

- שלושה אירועים בלבד: `message.received` · `message.sent` · `message.updated`.
- כישלון (לא 2xx) גורר ניסיון חוזר עם השהיה מתגברת, עד הצלחה.
- 🔴🔴 **כתובת שנכשלת ברצף מושבתת אוטומטית.** מאותו רגע תשובות הלקוחות
  מפסיקות להגיע: אין שגיאה, אין שורה ביומן, והמערכת נראית בדיוק כמו
  יום שקט. ההפעלה מחדש ידנית בהגדרות של heyy.

### פיזור נמדד: כל הודעה יוצאת מייצרת ~4.6 קריאות אלינו

מתוך 246 האירועים ביומן:

| אירוע | קריאות | הודעות שונות | יחס |
|---|---|---|---|
| `message.updated` | 183 | 51 | **3.59** |
| `message.sent` | 50 | 50 | 1.00 |
| `message.received` | 13 | 13 | 1.00 |

⭐ **והיחס הזה הוא מדד הבריאות הזול ביותר:** נכנסות ויוצאות ביחס 1:1
מדויק פירושו **אפס ניסיונות חוזרים**, כלומר האנדפוינט שלנו מעולם לא
נכשל. יחס גדול מ-1 ב-`message.received` הוא הסימן המוקדם לתקלה, עוד
לפני שמישהו מרגיש.

### הניטור

`supabase/functions/rashal-watchdog/` בודק כל שעה, שתי קריאות בלבד:

1. קיים וובהוק שמצביע על המערכת, **הוא `active`**, ויש בו את שלושת
   האירועים על הערוץ שלנו.
2. 🔴 הכתובת מכילה את הסוד (`?k=`). וובהוק בלי הסוד מקבל 401 מאיתנו על
   כל קריאה, ולכן heyy תשבית אותו בעצמה תוך זמן קצר.
3. הערוץ `active`, ודירוג האיכות במטא לא ירד.

⭐ **זו בדיקה חיובית ולא בדיקת שקט.** שקט בוואטסאפ הוא מצב תקין ביום
רגיל, ולכן "לא נכנסו הודעות" לעולם לא יכול לשמש כאות.
🔴 **"לא הצלחתי לשאול" אינו "תקין" ואינו "תקלה":** תקלת רשת אחת אינה
מעירה אף אחד, ורק שתי בדיקות רצופות שנכשלו שולחות מייל.

**אומת מקצה לקצה 26/08/2026:** הפניית הבדיקה לכתובת שגויה החזירה
`ALERT sent` ומייל אמיתי, והחזרת ההגדרה החזירה `RECOVERED` ומייל שני.
בדיקה שרק מוודאת שהמצב התקין נקרא תקין הייתה עוברת גם אילו הפונקציה
החזירה תמיד "בסדר".

## 4. 🔴 תאריך מת: API v2 נסגר ב-1 בנובמבר 2026

מדיניות ההוצאה משימוש של heyy היא **שלושה חודשים בלבד** מרגע פרסום
גרסה חדשה, והם נוקבים בתאריך מפורש.

### מה אצלנו רץ על הגרסה הישנה

| קובץ | מה עובר שם | נתיב |
|---|---|---|
| `api/_lib/heyy-server.ts` | טקסט חופשי · תבניות של הסקרים והתזכורות | `POST /api/v2.0/{channelId}/whatsapp_messages/send` |
| `api/wa-send.ts` (שורה ~325) | טקסט חופשי מתיבת השיחות | דרך `heyySendText` |
| `api/cron-daily-reminders.ts` | תזכורת יומית | דרך `heyySendTemplate` |
| `supabase/functions/rashal-surveys` | מנוע הסקרים | דרך `/api/heyy-send` |

**מה כבר על v3:** שליחת תבנית עם מדיה (`api/_lib/heyy-v3.ts`), משיכת
התבניות, והעלאת קבצים.

### החוזה של v3 לטקסט חופשי (אומת מול המפרט הרשמי)

```
POST https://api.heyy.io/v3/messages/send
{
  "chat": { "channelId": "<uuid>", "phoneNumber": "+9725..." },
  "body": "טקסט חופשי",
  "attachments": [ { "type": "image|video|document|audio", "fileId": "<uuid>" } ]
}
→ 200 { "success": true, "data": { "id", "chatId", "channelId", "sender": "outbound", ... } }
```

⭐ שני הבדלים מהותיים מהגרסה הישנה:
1. **הערוץ עובר בגוף** (`chat.channelId`) ולא בנתיב.
2. **המשתנים בתבניות הם אובייקט שטוח** `{שם: ערך}` ולא מערך
   `[{name, value}]`. שתי הצורות חיות אצלנו כרגע במקביל, וקל להעביר
   בטעות את המבנה של האחת לשנייה.

### התוכנית, לפי סדר

1. להוסיף `sendText()` ל-`api/_lib/heyy-v3.ts`, לצד `sendTemplate()`
   הקיים, עם אותו טיפול במכסה ואותו חילוץ מזהים.
2. **לאמת בשליחה אמיתית אחת** לנייד של עידן, ולוודא שני דברים: שחוזר
   `data.id`, ושהוובהוק מעדכן ממנו `delivered` ואז `read`.
   🔴 **בלי המזהה אין מעקב מסירה בכלל**, וזו בדיוק התקלה שעלתה לנו
   ביוקר ב-20/08 כשהקוד קרא שדה שלא קיים בסכימה.
3. להעביר את `heyySendText` לקרוא ל-`sendText`, ולהשאיר את החתימה
   בדיוק כפי שהיא כדי ששלושת הקוראים לא ישתנו.
4. להעביר את `heyySendTemplate` ל-`sendTemplate` של v3, **ולהמיר את
   מבנה המשתנים** מהמערך לאובייקט. זה השינוי המסוכן, כי משתנה שלא
   הומר מגיע ריק ללקוח בלי שום שגיאה.
5. למחוק את `HEYY_BASE` ואת המסלול הישן, ולוודא שאין יותר אזכור
   ל-`api/v2.0` בקוד.

**חלון:** לבצע עד סוף ספטמבר, ולא באוקטובר. אם משהו יישבר בהגירה,
צריך זמן לתקן לפני שהנתיב הישן מפסיק לענות.
